## 1. Executive Summary & Core Architecture

The **Rotterdam Live API** (`rotterdam-live-api`) is an asynchronous, high-throughput geospatial platform engineered to power the real-time situational map of Rotterdam (`rott-live`). It serves as the single source of truth for all situational, municipal, commercial, environmental, meteorological, cultural event, crowdness, and traffic intelligence across the municipality of Rotterdam (Gemeentecode `0599`).

The database currently holds **over 396,400 spatial records** indexed with PostGIS GiST and PostgreSQL `pg_trgm` GIN indexes.

## 3. The Real-Time Traffic Engine & Mobility Subsystem (Platform v2.0.0-rc)

### Architectural Invariant: Zero In-Request Computation
The API endpoints return in **< 5ms** from Redis cache (**< 30ms** on cache-miss from indexed tables). 
**Never compute spatial joins, LineString clipping, or travel time regressions during client HTTP requests.**
- The background harvester (`RotterdamTrafficHarvester`) polls external NDW feeds and diurnal baseline engines every 60 seconds.
- Pre-compiles master LineString FeatureCollections and overview statistics directly into Redis (`mobility:traffic:live`, `mobility:traffic:overview`, `mobility:traffic:segment:{id}`).
- The API router (`app/api/v1/mobility.py`) strictly reads pre-compiled JSON snapshots with RFC 7232 ETag conditional caching.

### Quantitative Traffic Model & Congestion Tiers

Target metrics:
- Vehicle Speed: $v \in [0, 130]\text{ km/h}$
- Speed Ratio: $r = \frac{v}{v_{\text{free}}}$
- Traversal Duration: $t_{\text{travel}} = \frac{t_{\text{free}}}{\max(0.15, r)}$
- Traversal Delay: $\text{delay} = \max(0, t_{\text{travel}} - t_{\text{free}})$

**Congestion Severity Tiers:**
- `free_flow` ($r \ge 0.85$): Fluid conditions, delay $\approx 0$. Color: `#10b981` (Green).
- `moderate` ($0.60 \le r < 0.85$): Traffic slowing, minor queues. Color: `#f59e0b` (Amber).
- `heavy` ($0.30 \le r < 0.60$): Major delay, stop-and-go congestion. Color: `#f97316` (Orange).
- `standstill` ($r < 0.30$): Gridlock / incident blockages. Color: `#ef4444` (Red).

## 4. The Production-Grade Crowdness Engine & Real-Time Forecaster (Platform v1.9.0)

Target metric: Normalized Crowdness Index $\mathcal{C} \in [0, 100]$.
- `0 - 25`: Quiet (Rustig)
- `26 - 50`: Moderate (Normaal)
- `51 - 75`: Busy (Druk)
- `76 - 100`: Saturated / Peak (Zeer druk / Piek)

### Quantitative Model Specification
- **Live Residual:** $\Delta_d(t_0) = \mathcal{C}_{\text{live}}(d, t_0) - \hat{\mathcal{C}}_d(t_0)$
- **Horizon Forecast:** $\mathcal{C}_d(t_0 + h) = \text{Clamp}\Big(\hat{\mathcal{C}}_d(t_0 + h) + \Delta_d(t_0) \times e^{-0.5 h}, \, 0, \, 100\Big)$
- **Strict Invariant:** At $h=0$, $\mathcal{C}_d(t_0) \equiv \mathcal{C}_{\text{live}}(d, t_0)$ with zero double-counting.

## 8. Events Domain Temporal Filtering & Stadium Venue Telemetry (Platform v2.1.0)

### Temporal Query Invariants
To preserve historical event data in PostgreSQL while guaranteeing clients receive only upcoming or currently active items:
1. **Default Temporal Filter:**
   `GET /api/v1/events`, `GET /api/v1/events/fixtures`, `GET /api/v1/events/today`, and `GET /api/v1/events/festivals` expose `include_past: bool = False` (default: `False`).
   - Active/upcoming query filter:
     ```sql
     WHERE COALESCE(end_time, start_time + INTERVAL '3 hours') >= NOW()
     ORDER BY start_time ASC
     ```
   - All historical events remain safely stored in `rotterdam_events`.
2. **Separation of Stadiums vs Fixtures:**
   - **`GET /api/v1/events/fixtures`**: Returns RFC 7946 GeoJSON points for upcoming matches (`stadium_fixture`).
   - **`GET /api/v1/events/stadiums`**: Returns RFC 7946 GeoJSON FeatureCollection of the 3 physical stadium venues (`stadium-de-kuip`, `stadium-het-kasteel`, `stadium-woudestein`) with stadium capacity, club name, address, total fixtures count, and real-time joined `next_fixture` telemetry.
3. **Strict Live Events Feed Isolation:**
   - In `app/services/spatial_service.py`, `GET /api/v1/live?category=event` enforces:
     ```sql
     WHERE timestamp <= NOW() AND COALESCE(expires_at, timestamp + INTERVAL '3 hours') >= NOW()
     ```
     This strictly prevents scheduled future events from polluting the real-time operational live map layer.

## 9. Real-Time Crowdness Cadence & Telemetry Accuracy Audit

### High-Frequency Polling Upgrade
- Background daemon calculation cadence reduced from 600s (10m) to **120s (2m)** (`CROWD_POLL_INTERVAL_SECONDS = 120`).
- Redis cache TTL reduced to **180s** (snapshots) and **120s** (fallbacks), ensuring the crowdness choropleth reacts promptly to garage occupancy shifts, traffic delays, and incoming rain bands.

### Live Accuracy Terminal Audit Findings
An exhaustive terminal audit verified live crowdness numbers in Redis/Postgres against ground-truth sensor inputs:
- **Centrum District:** Weighted parking garage occupancy = **77.53%** across 7 monitored garages (e.g. Bijenkorf, Erasmus, Schouwburgplein). With dry weather (+4 pts shift) and no active incidents:
  $$\mathcal{C}_{\text{live}}(\text{Centrum}) = \text{Clamp}(0.75 \times 77.53 + 4.0, 0, 100) = \mathbf{62.12}\text{ pts}$$
  Matches live Redis snapshot (`62.12`) with **0.00% error**.
- **Charlois District:** Parking garage occupancy = **73.0%** (Zuidplein).
  $$\mathcal{C}_{\text{live}}(\text{Charlois}) = \text{Clamp}(0.75 \times 73.0 + 0.75, 0, 100) = \mathbf{55.50}\text{ pts}$$
  Matches live Redis snapshot (`55.50`) with **0.00% error**.
- **Sensorless Districts:** $\Delta_d(t_0) = 0$ holds true; baseline derived from diurnal prior + weather shift with residual $\approx 0$.
