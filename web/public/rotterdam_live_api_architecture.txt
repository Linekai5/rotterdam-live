# Rotterdam Live — City Explorer & Live Weather Architecture

Architecture revision 2.5.0 · 5 November 2026 · Development branch: `malidev`

This public overview describes the current development implementation. The session
changes have not been deployed to production. The full repository specification is
`rotterdam_live_api_architecture.txt` at the repository root; its repository mirrors
are `api/rotterdam_live_api_architecture.txt` and
`docs/artifacts/rotterdam_live_master_architecture.md`.

## Data flow

Open-Meteo / KNMI model samples, Buienradar station observations and point rain
predictions, and RainViewer radar metadata enter background weather harvesters.
The worker validates and normalizes them into Redis snapshots. Station records
also update PostGIS amenities and live events. FastAPI serves the snapshots to the
Svelte / MapLibre frontend. The browser retrieves radar image tiles from RainViewer.

Local development uses Vite on port 5173. Its `/api` and `/health` proxy forwards
to FastAPI on port 8000. The browser requests model weather every minute, radar
metadata only while enabled, and health every ten seconds. Ingestion refreshes the model grid every two minutes,
point rain/radar metadata every five minutes, and stations every ten minutes.
Polling cadence is separate from the model valid time and provider update cadence.

## On-demand city explorer

The charcoal explorer has Map layers, In view and Map sections, with muted sage,
sand and clay accents. Every optional data layer starts off. Users can select
events, neighbourhoods, shops, useful facilities, traffic, parking, bridges,
roadworks, estimated district activity, emergency reports, local news and
environmental records. City pulse is a model estimate, not a count of people;
directories and annual statistics are labelled separately from current reports.

Selected layers use the existing GeoJSON API, with two explorer requests at a
time, a 400ms map-movement debounce, cancellation and a bounded 45-second cache.
Most feeds request the current bounding box and at most 150 records; a notice
asks users to zoom in when the cap is reached. Point clusters and an explicit
Show more keep dense results manageable. Loading, stale, error and retry states
are visible. Selected feeds refresh every minute while the page is visible.

Search is debounced and supports Cmd/Ctrl+K and keyboard selection. Location
details show typed metrics, source timestamps and safe source links. District
profiles are requested only when opened and show the year of annual statistics.
Aerial, Night and Atlas maps retain selected layers and preferences. The desktop
panel can collapse; mobile uses an explorer sheet and a location sheet. Short
panel/camera transitions respect reduced motion, including freezing idle cloud
animation. No AI supervisor is mounted or requested.

## Weather contracts

- `/api/v1/weather/live`: station/model overview, existing 12-node model grid,
  solar position, source and freshness status.
- `/api/v1/weather/grid`: the same 12-point spatial sample mesh as structured nodes
  and GeoJSON features. It is not a network of 12 observation stations.
- `/api/v1/weather/stations` and `/stations/{station_id}`: point observations.
- `/api/v1/weather/rain-forecast`: approximately two hours of five-minute point
  predictions, with dated UTC slot timestamps and an explicit availability status.
- `/api/v1/weather/radar`: radar frame metadata, with `latest_frame` chosen only
  from past frames. The UI shows the latest observed frame, not a future timeline.

Every requested model field must be numeric and finite, with a valid model time
and positive accumulation interval. Precipitation amounts become interval-average
hourly rates using `amount * 3600 / interval`. Model and observation times remain
separate from response assembly time. A failed provider fetch does not produce
invented weather or an all-dry rain prediction.

Grid/live snapshots have a 120-second TTL. Labelled last-good snapshots can be
retained for a day, preserving their original timestamps. Point-rain/radar cache
TTLs are five minutes; station snapshots use ten minutes. Weather routes still
harvest on cache misses, so cache-hit latency targets do not cover cold requests.

## Live UI and observed rain

The controller requires a complete validated grid, source times, solar angles,
and explicit freshness status. It starts without weather values. Accepted data
older than 30 minutes, more than five minutes in the future, labelled stale by the
backend, or followed by a failed refresh becomes outdated. Model cloud effects
stop while stale; prior values can remain visible with their original time.

The muted charcoal card consistently shows Rotterdam Centrum model values:
temperature, weather description, wind speed/direction, cloud cover and rain rate.
It shows Live / Outdated / Unavailable, a Rotterdam-local valid time, source details,
manual refresh and radar attribution. There are no presets or simulator controls.

Observed rain uses a separate raster layer. Radar frames older than 20 minutes or
more than five minutes in the future are removed. Source zoom is capped at 7;
further map zoom does not create additional radar detail. Frame time is composite
metadata and is not necessarily every radar pixel's observation time.

## Cloud appearance

The final cloud renderer uses two continuous 3D density fields, with 16 depth
samples per deck and two density probes toward the sun for self-shadowing. A
regional envelope, multiple scales of noise, vertical taper and erosion produce
cloud bodies, irregular edges and gaps. Light transmission supplies lit crowns,
shaded interiors and translucent edges. Colour/alpha accumulate front-to-back.

The lower visual deck combines low and middle cloud cover at fixed illustrative
heights of 900–2400m. The upper deck uses high cover at 3000–3650m. These are not
observed cloud heights. Approximate camera projection creates parallax; model 10m
wind drives drift. The canopy fades with zoom to expose street details.

Clouds are rendered into a reduced-resolution framebuffer and composited over the
map. The long edge is capped at 920 pixels at rest and 640 during map movement,
with a 33ms idle repaint timer. Performance depends on the device; a short local
browser sample measured approximately 30 FPS, not a universal 60 FPS guarantee.

Generated rain streaks and random lightning flashes were removed. Fog geography
remains illustrative. Model storm flags are metadata, not observed lightning or
calibrated probabilities. Cloud cover percentage is not a map opacity target.
Cloud shape and position remain procedural, without a satellite mask.

Rain radar starts off and loads metadata/tiles only after it is enabled in Map.
Its switch is independent of cloud atmosphere. Native map credits remain visible
or available through the attribution control, including on small screens.
The original volumetric clouds remain enabled by default on Aerial and across
map-style changes. Zero model cloud cover gives a clear sky; the map does not add
decorative clouds over a clear live-model snapshot.

## Session verification and remaining work

The November frontend checks passed: ten unit/spatial tests, eighteen browser
checks (explorer, mobile, map/ocean lifecycle and clouds), and the Vite build.
The earlier October weather session also passed 32 relevant backend weather/crowd
tests; the backend suite was not rerun as part of the frontend-only work.
The browser regression checks a compiled shader and actual framebuffer pixels,
including cloud bodies and gaps; layer registration alone is insufficient.
Overhead/tilted screenshots and desktop/mobile layout were inspected locally.

These checks verify software behaviour, not forecast accuracy. Satellite cloud
outlines, cloud-level winds/heights, regular-grid expansion, station bias correction,
direct KNMI spatial radar integration and multi-week accuracy measurement remain
future work. A push to `malidev` does not trigger the `main` production workflow.
The former `feat/live-spatial-weather` branch has been removed; its history and
the development changes are retained on `malidev`.
